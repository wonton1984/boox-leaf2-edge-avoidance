# 实测范围与限制

本项目来自一台 BOOX Leaf2_P 的单设备试验，不代表全系列兼容。

| 项目 | 实测 |
| --- | --- |
| 系统 | Android 11 / API 30 |
| 固件 | `2025-11-26_19-25_4.0.2-rel_0621_da686c4b1` |
| 物理屏幕 | 1264×1680，density 300 |
| Root | Magisk 31.1；这里只记录已具备的运行条件，不提供刷机流程 |
| 参数 | 自然方向 ROTATION_0 的右侧 140px |
| 逻辑尺寸 | 1124×1680 |
| 0° | 显示/输入 logicalFrame=(0,0,1124,1680)，physicalFrame=(0,0,1124,1680) |
| 180° | orientation=2，logicalFrame=(0,0,1124,1680)，physicalFrame=(140,0,1264,1680) |
| 系统与输入法 | 系统设置搜索框可输入测试文字；输入法窗口1124×1680 |
| 微信读书 | 墨水屏版 `com.tencent.weread.eink` 阅读Activity窗口1124×1680，0/180°投影检查通过 |
| 热停用 | 关闭RRO后显示与输入恢复1264×1680 |
| 模块停用 | disable标记重启后APK不挂载，恢复完整尺寸 |
| 重启持久化 | RRO保持启用，稳定后显示与输入均1124×1680 |

180°的physicalFrame使用旋转后的坐标系；结合orientation=2，排除的仍是同一物理坏边。正常对边没有另加裁剪。

启动早期观察到窗口管理器短暂保留1264宽度，底层已使用1124宽度，出现上下留边；之后无需额外命令自行刷新为正确尺寸。项目未添加启动脚本来掩盖这个过程，不能保证开机动画或启动过渡始终避让。

**尚未完成的验收：**物理损坏是否被140px完全覆盖、真实手指触摸与翻页手感，需要现场用户确认。窗口几何和注入文字不是物理触摸验收。原校准图在图库中存在缩放，最终采用用户明确指定的140物理像素，不能把该值当作其他设备的通用测量。

右侧140px是实测配置；生成器支持左侧与其他宽度，但这些配置没有实机验证。左右边以自然方向为准，不按当前倒置画面判断。

原试验使用本机已有framework资源进行链接、局部APK v2签名程序签名；发布工程改用官方SDK android.jar和apksigner，不携带厂商资源、原签名密钥或原二进制。发布工程的完整官方工具构建链尚未在本工作环境端到端执行；不要声称生成的APK与原试验包字节一致。

结束时恢复了原自动旋转设置，并通过Magisk界面撤销临时Shell root；su id被拒绝。未更改AVB/SELinux，也没有给其他应用授予root。

## 发布前本地构建检查

- 生成器左右140px配置均生成四项资源，XML解析通过。
- 使用现有官方AAPT2 36对左右配置编译、链接通过；链接参考的是本地已有厂商framework，测试二进制随后丢弃，参考文件未进入仓库。
- 构建入口的0、负数、超宽参数被拒绝，未创建输出目录。
- 当前环境缺少Java Runtime和SDK Platform Android 30的android.jar，故未完成发布构建脚本的官方SDK平台链接与apksigner签名全过程。README列出完整依赖，未为本次发布安装新软件。
